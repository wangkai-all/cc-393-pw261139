# 区间回补 · 删除屏障 控制台

虚构数据处理演示：离线区间回补会读取历史原始包，但部分记录后来收到了删除请求。
本项目实现**删除登记服务、回补进程、发布端**三方协调，保证任何已删除记录都不会
进入可分发区——即使删除发生在**计算完成与发布之间**，即使**登记服务短暂离线**。

纯 Python 标准库实现，无第三方依赖。

## 运行

```bash
python3 run.py serve        # 删除登记服务 :8601 + 控制台 :8600
python3 run.py init-data    # （可选）命令行生成封存原始包；也可在网页上点按钮
python3 run.py verify       # 校验封存完整性（原始包哈希 + 审计链）
python3 tests/test_scenarios.py   # 端到端场景测试（37 项断言）
```

打开 http://127.0.0.1:8600 ，页面上可以：**提交删除、发起区间回补、让删除服务
短暂离线、查看哪些结果被阻断及恢复依据**。

## 为什么“回补开始时查一次名单”不够

回补读的是旧原始包，删除请求却在持续到达。只在开始时查一次名单，管不到三个窗口：

| 窗口 | 本方案的机制 |
|---|---|
| 计算期间到达的删除 | FINALIZE 阶段读 `deletions since v_start`，过滤后给结果盖**删除屏障**版本 |
| 计算完成与发布之间到达的删除 | 发布端持锁重读名单快照，屏障版本落后则在**发布屏障**处过滤（或阻断） |
| 发布之后到达的删除 | 登记删除即触发**修订扫描**：已发布版本撤回封存，发布过滤后的修订版 |

而登记服务离线时，以上任何一步都拿不到“结果干净”的证明 → 一律 **fail-closed 阻断**，
恢复后凭版本比对放行，阻断原因与恢复依据都写入审计链并在页面可见。

## 协调协议

- **删除的线性化点** = 登记服务分配版本号（`POST /v1/deletions` 返回，幂等）。
- **发布的线性化点** = 发布锁内向登记服务读取的一致性快照版本。
- 发布临界区与修订扫描共用同一把锁：删除先登记、后扫描，因此任何已登记删除
  要么被发布屏障的快照看到，要么被修订扫描兜底，**不存在漏网窗口**。
- 删除登记成功但扫描失败（服务在两者之间宕掉）→ 扫描延期，服务恢复后自动补扫；
  登记服务离线时删除**不被受理**（明确报错），绝不静默丢失。

回补状态机：`PREPARE → COMPUTING → COMPUTED → (FINALIZE) → PENDING → PUBLISHED`，
失败分支 `BLOCKED_PREPARE / BLOCKED_FINALIZE`（可恢复）、`FAILED_INTEGRITY`（篡改）。

## 封存区 vs 可分发区

```
data/
  sealed/               历史封存（审计侧）——只增不改
    raw/                原始包：封存时算 sha256 写入 manifest 与审计链，文件置只读
    withdrawn/          被撤回的可分发版本（单向迁入留档，哈希入审计链）
    audit.jsonl         哈希链审计日志（每条含前条哈希，篡改即断链）
  distributable/        可分发区（消费侧）——删除语义只作用在这里
    published/          当前生效结果（含聚合、血缘 record_id 清单、屏障版本）
    index.json          生效版本索引
  state/                运行态：登记服务镜像、回补运行、待发布结果
```

**不能靠篡改原始包掩盖处理问题**：回补读取每个原始包前都重算哈希比对封存清单，
清单哈希又锚定在审计链里。篡改 → 回补中止（`FAILED_INTEGRITY`）+ 校验报警 +
审计链永久留痕，即使事后把文件改回去，失败记录也抹不掉（见场景测试 8）。

## 页面演示剧本

1. **生成封存原始包**（6 包 × 12 条虚构配送事件）。
2. 发起区间回补 `1–3` → 待发布 → 发布（屏障 v0）。
3. 提交删除 `R0002-03` → 已发布结果立即出 v2 修订版，v1 撤回封存区留档。
4. 发起回补 `1–6` → 待发布后**先别发**；提交一条 4–6 号包记录的删除 →
   再点发布：屏障发现版本落后，过滤后按新屏障发布（审计 `PUBLISH_BARRIER_FILTER`）。
5. 点 **让删除服务离线** → 发起回补或发布 → 全部阻断，页面显示阻断原因与恢复条件；
   离线期间提交删除会被**拒绝受理**。
6. 点 **恢复上线** → 自动补扫可分发区；对被阻断项点 **恢复/发布** →
   放行依据（版本比对结果）写入审计并显示在页面上。
7. 点 **校验封存完整性**：重算全部原始包哈希 + 重放审计链。

```
app/pipeline.py       核心域逻辑：封存、回补状态机、发布屏障、修订扫描、完整性校验
app/web.py            控制台页面 + 编排 API
tests/test_scenarios.py  端到端场景测试
```
